# 新增赛题指南

新增赛题通常分四步。**创建任务包 → 写明验收与计分规则 → 验证评测链路 → 登记题集版本。** 下面以整网模型部署题为例，说明怎样把题目要求转成可执行的评测条件。相同流程也适用于算子生成、性能优化、缺陷诊断和修复。

## 1. 创建任务包

复制一个最接近的示例到 `tasks/<task-id>/`。更新目录名、`task.yaml` 中的 ID、版本和资产路径，先将状态设为 `draft`。路径相对于仓库根目录。

| 要填写的内容 | 确认什么 |
|---|---|
| 任务目标和范围 | 用 `objective` 表达要完成的工作，用 `scope` 表达算子、子图或整网。例如整网部署验收可写 `implement / model`；已有实现上做性能优化可写 `optimize / model`。 |
| 问题、接口与提交 | 写清输入、输出、成功条件、提交工件或入口，以及允许和禁止修改的范围。选手应能提前理解哪些行为会导致提交无效。 |
| 工作负载 | 声明公开用例、强制场景和覆盖范围。为用例保留稳定 ID，并区分正式计分场景和诊断场景。 |
| 正确性依据与答案示例 | 提供可信的参考实现、标签或检查依据，以及能复现验收流程的 `answer_example`。按需提供起始代码和固定性能基线。 |
| 验证环境和硬件 | 记录已验证平台、环境版本、最低卡数、显存、主机内存和互联要求。推荐配置可选，尚待实测的要求先留空。 |

可参考 [ReLU 任务包](../../tasks/example.operator.relu/)、[分类模型优化任务包](../../tasks/example.model.classifier/) 和 [任务包契约](../spec/task_package.md)。

## 2. 先定义验收，再定义计分

**验收标准**决定提交和结果是否有效。每条都写清检查对象、通过阈值、适用用例及失败结果。**计分方式**决定有效结果如何排名。只考任务能否完成时，可以只报告通过率或通过／失败。

| 评测层次 | 规则 | 整网模型部署题示例 |
|---|---|---|
| 提交验收 | 检查格式、入口、修改范围和资源约束 | 在声明的平台上能通过就绪检查，并完成首个真实请求 |
| 正确性或质量验收 | 用参考或标签检查强制用例，预先约定阈值 | 输出符合服务接口，模型质量较官方参考下降在公布的容差内 |
| 完整性与计分资格 | 检查必跑用例、报告和指标，区分候选失败与基础设施故障 | 指定并发场景全部完成，成功率和峰值显存符合限制 |
| 排名指标 | 固定指标、单位、方向、测量边界和聚合规则 | 当题目考查部署性能时，按端到端 P95 延迟或满足服务门槛的有效吞吐排名 |

失败和缺测规则要随赛题一起公开。候选错误、超时或超资源按题目规则处理；基础设施故障单独归因，可依预先规定的方式重试；只跑了部分强制用例的结果要标记为不完整。固定用例权重和分母，避免提交因漏跑困难用例而提分。

### 评分规则放在哪里

| 位置 | 职责 |
|---|---|
| `scoring/` | 集中维护计分公式、用例聚合、失败与缺测规则，并按版本发布。 |
| `tasks/<task-id>/` | 用 `evaluation.scoring_rule` 引用固定版本，声明本题的阈值、基线、必跑用例和测量配置。题目说明应让选手能找到完整规则。 |
| `suites/` | 固定题目版本，并在需要总榜时声明跨题权重、聚合方法和失败项如何进入分母。 |

例如，两道性能题可以共享 `基线耗时 / 候选耗时`。算子题可以用 kernel 耗时，整网题可以用从输入就绪到完整输出可用的端到端耗时，各自冻结测量边界。若整网题有两个强制场景，权重为 60% 和 40%，候选通过验收后得到 1.25×、1.20×，加权几何平均为 `1.25^0.60 × 1.20^0.40 ≈ 1.230×`。如果题集要汇总不同指标，先约定各题如何映射到总分，并同时展示完成率和原始指标。

骨架中的 [耗时比规则](../../scoring/latency-ratio.v1.yaml) 使用中位耗时和等权聚合。采用 P95 或不同权重时，制定对应版本，并在评测器中实现该口径。

## 3. 验证评测链路

1. 复用能处理本题契约的评测适配器，或在 `src/cannbench/adapters/` 新增适配器并注册到 [Engine](../../src/cannbench/engine.py)。任务包声明对应的适配器和提交类型。
2. 在仓库根目录运行 `PYTHONPATH=src python -m cannbench validate --schema`，检查清单和引用路径。用 `plan` 核对任务与候选参数，再用评测器执行验收。模板 CLI 通过 `--source-dir` 接收源码工程，其他提交形式需要对应入口。
3. 在声明的平台上用答案示例跑完正式用例。性能题还要验证官方基线能在同一环境下复现。随后验证错误提交、超时或资源超限、漏跑和基础设施异常，确认报告如实区分正确性、计分资格和失败原因。

报告至少应包含任务与规则版本、用例执行结果、门槛与实测值、失败类型、计分资格及成绩。性能题同时保留基线、环境与测量配置身份，以及原始数据或可复查的统计记录。

## 4. 登记题集并发布

验收通过后，在 `suites/*.yaml` 引用任务 ID 和固定版本，再按发布流程登记正式题集。检查选手能从题面找到完整输入、修改边界、答案示例、硬件要求和计分规则。发布时冻结任务、规则、基线、负载和评测环境，后续修改形成新版本，历史成绩继续绑定原版本。[示例题集](../../suites/examples.yaml)

## 5. 待讨论事项：以整网模型赛题为例

下列问题需要出题团队与评测平台共同确认。建议先用官方基线和答案示例做一轮试测，再根据质量、耗时和设备占用确定规则。这里列出的选项供评审讨论。

### 5.1 模型精度怎么评，完整评测集会不会太耗时？

- **按题目目标选精度指标。** 要求实现与原模型等价时，可以在代表性输入上比对 logits、张量或任务输出，并固定容差。允许量化、换算子或改变计算精度时，可用固定数据集上的任务指标衡量质量，例如分类准确率。要确认是设绝对最低线，还是允许相对参考模型下降一定幅度，并标明用百分比还是百分点。
- **先测成本，再决定数据量。** 对候选和基线固定数据版本、预处理、采样或解码参数及指标实现。试测小样本、分层子集和全量数据的墙钟时间，并看子集是否会误放或误拒接近门槛的提交。小样本适合快速反馈，全量或经验证的固定子集可用于正式验收。若将全量评测留到复核阶段，应提前写明哪些提交会进入复核、榜单何时生效。
- **待拍板。** 使用哪套数据与指标、最低线怎么设、正式验收跑多少样本、单次精度评测预算和临界结果复核方式。用于正式排名的提交应采用一致的精度口径。

### 5.2 是否必须多卡、多机，平台能支持多大的评测预算？

- **先定最低可运行拓扑。** 确认模型及场景是否在单卡、单机多卡或多机多卡上才能满足要求。跨机能力若是赛题要考察的内容，再定义节点数、每节点卡数、互联和网络条件。
- **按实际设备池核算。** 平台确认能同时分配多少组满足卡型、显存和拓扑的资源，以及峰值提交量下可承受的排队时间。零散空闲卡无法替代同机互联或跨机成组资源。资源不足时可讨论缩小首批规模、限流，或将多机评测单独设赛道。
- **待拍板。** 首批硬件范围和并发任务数。单次评测需要设总墙钟上限，并明确构建、初始化、精度、性能及资源回收各自的时间预算，排队时间是否单独统计，超时与平台故障如何归因。根据试测的慢场景定上限，同时核算每个提交占用的卡时。

### 5.3 哪些内容可改，哪些内容必须固定？

在题目契约中逐项列出固定项、允许改动的内容及验证方法。至少要讨论模型权重和数值语义、权重存储格式及预打包、ND/NZ 布局转换、图调用路径、融合与并行策略，以及缓存和计时边界。例如，允许把权重从 ND 转为 NZ 时，要说清转换是离线完成还是计入评测，产物如何提交，是否允许改变权重数值。

| 可改范围 | 题目和评测需要配套什么 |
|---|---|
| **较窄**，例如固定权重格式和图调用路径，只允许修改指定实现 | 提供明确的文件与接口清单、固定脚本、示例工程和必要配置，让选手能复现同一入口及检查结果 |
| **较宽**，例如允许重排权重、替换图调用路径、使用不同融合或并行方式 | 固定外部输入输出、质量、资源及计时边界。评测端需能核对实际执行路径、隔离可信资产，并覆盖结果复用或跳过计算等行为 |

**待拍板。** 每一项的改动权限、可改工件及对照证据。放宽某项限制前，要确认现有评测器能否验证等价性及约束，预计还要补多少反作弊和验收工作。

### 5.4 性能测什么，以服务还是整网脚本作为入口？

先选与赛题目标相符的执行形态与排名指标。服务化评测能体现排队、并发和尾延迟，需固定压测客户端与请求调度。整网脚本适用于离线或固定负载，需明确从哪个阶段开始计时、何时认定结果已完成。

| 目标 | 负载及排名口径 |
|---|---|
| **极低时延** | 固定并发或请求到达率、输入输出分布及成功率门槛，按端到端 P95 等延迟指标排名。流式模型可单独报告首 token 延迟 |
| **极大吞吐** | 固定设备预算、请求分布和服务门槛，按单位时间内成功且符合时延要求的请求数或样本数排名 |
| **最快跑完整个评测集** | 固定样本集、覆盖范围及正确性门槛，按从约定起点到全部结果可用的总墙钟时间排名。明确是否含加载、预处理和写出 |

**待拍板。** 选服务接口还是整网脚本，公布主指标与辅助指标。固定设备与拓扑、软件版本、负载、并发、预热和缓存，说明数据传输、排队、设备同步、跨卡通信及前后处理是否计时。若低延迟和高吞吐都要评，可分别固定各自负载和门槛，按场景出成绩。
